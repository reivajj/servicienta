01 · ¿Qué es?

Por qué Turborepo

Un sistema de build inteligente que unifica tu código sin cambiar cómo deployás cada servicio.

⚡

Caché inteligente

Crea un hash del contenido de tus archivos. Si nada cambió, restaura el output anterior. Builds de 15 min → 2 min.

📦

Código compartido

Tipos TS, cliente Supabase y validators Zod viven en un solo lugar. Cambiás uno, se actualiza en todos.

🔗

Dependencias automáticas

Turborepo sabe en qué orden compilar. Si packages/types cambia, reconstruye todo lo que depende de él.

🚀

Deploy independiente

El monorepo es solo para desarrollo. Cada app sigue deployándose a su propio servidor sin cambios.

🔍

Errores inmediatos

Un cambio roto que antes pasaba entre repos ahora falla en TypeScript en el mismo momento.

🧩

Paralelo por defecto

Corre tareas en paralelo cuando no hay dependencias entre ellas. Dev de 6 apps arranca al mismo tiempo.

02 · Estructura

Cómo queda
tu proyecto

Dos carpetas raíz: apps/ para lo que se deploya, packages/ para código compartido interno.

my-project/ ← raíz del monorepo ├── apps/ │ ├── web/ ← React + Vite (SPA, auth) │ ├── landing/ ← Next.js (SSR, público) │ ├── api-gateway/ ← Node/Express API │ ├── service-users/ ← Microservicio 1 │ ├── service-orders/ ← Microservicio 2 │ └── service-notifications/ ← Microservicio 3 │ ├── packages/ │ ├── types/ ← DTOs, interfaces TS │ ├── supabase/ ← cliente + helpers auth │ ├── api-client/ ← fetchers tipados │ ├── query-hooks/ ← hooks TanStack Query │ ├── validators/ ← schemas Zod │ └── config/ ← ESLint, TS base │ ├── turbo.json ← el cerebro ├── package.json ← workspaces └── pnpm-workspace.yaml ← recomendado
⚡

apps/web — React + Vite

SPA con rutas protegidas por auth de Supabase. Corre 100% en el browser. TanStack Query para server state.

🌐

apps/landing — Next.js SSR

Público, indexable. Puede obtener datos dinámicos (técnicos disponibles, etc.) en el servidor antes de renderizar la página.

📦

packages/ — librerías internas

Compartidas por ambas apps y los servicios. api-client funciona tanto en browser (Vite) como en servidor (Next.js).

🧠

turbo.json — el pipeline

Define tareas, orden de compilación y caché. Buildea packages/ antes que apps/ automáticamente.

03 · Conceptos clave

Las 3 cosas que
tenés que entender

Todo Turborepo se reduce a estos tres conceptos.

01

workspaceWorkspaces

Cada carpeta en apps/ y packages/ es un workspace independiente. Se referencian entre sí por nombre en el package.json.

apps/web/package.json
{
  "name": "web",
  "dependencies": {
    "@myproject/types": "*",
    "@myproject/api-client": "*",
    "@myproject/query-hooks": "*"
  }
}
pnpm-workspace.yaml
packages:
  - "apps/*"
  - "packages/*"
02

pipelineturbo.json — El pipeline

Define el grafo de tareas y sus dependencias. El ^ significa "primero compilá mis dependencias".

turbo.json
{
  "tasks": {
    "build": {
      // ^ = primero buildea dependencias
      "dependsOn": ["^build"],
      "outputs": ["dist/**"]
    },
    "dev": {
      "cache": false,
      "persistent": true
    },
    "test": {
      "outputs": ["coverage/**"]
    }
  }
}
⚡ CLAVE: Con "dependsOn": ["^build"], Turborepo buildea packages/types antes que cualquier app que lo use. Automático.
03

cachingCaché inteligente

Cada task genera un hash del contenido de archivos + dependencias + config. Si el hash ya existe, restaura el output sin re-ejecutar.

primera vez vs segunda vez
# Primera vez: ejecuta todo
$ turbo build
  packages/types:build    → compiled
  apps/api-gateway:build  → compiled
  apps/web:build          → compiled
  Time: 47s

# Sin cambios: usa caché
$ turbo build
  packages/types:build    → cache hit ✓
  apps/api-gateway:build  → cache hit ✓
  apps/web:build          → cache hit ✓
  Time: 0.4s
🌐 Remote Cache: Con turbo.build o tu propio servidor, la caché se comparte entre tu máquina y CI.

🔑 La diferencia clave

En apps/web (Vite), el HTML llega vacío y React lo llena en el browser — requiere auth antes de mostrar contenido. En apps/landing (Next.js), el servidor renderiza el HTML completo con los datos ya incluidos — Google lo indexa, el usuario lo ve instantáneamente.

apps/web — rutas protegidas con Supabase auth
// apps/web/src/components/ProtectedRoute.tsx
import { supabase } from '@myproject/supabase'
import { useEffect, useState } from 'react'
import { Navigate } from 'react-router-dom'

export function ProtectedRoute({ children }: { children: React.ReactNode }) {
  const [session, setSession] = useState(null)
  const [loading, setLoading] = useState(true)

  useEffect(() => {
    // Lee la sesión actual de Supabase
    supabase.auth.getSession().then(({ data }) => {
      setSession(data.session)
      setLoading(false)
    })
    // Escucha cambios de sesión (login / logout)
    const { data: { subscription } } = supabase.auth.onAuthStateChange(
      (_, session) => setSession(session)
    )
    return () => subscription.unsubscribe()
  }, [])

  if (loading) return <Spinner />
  if (!session) return <Navigate to="/login" />
  return <>{children}</>
}
apps/landing — obtener datos dinámicos en el servidor (Next.js App Router)

⚠️ Diferencia importante: cómo usa api-client cada app

Vite (browser): apiFetch usa import.meta.env.VITE_API_URL y lee el token de Supabase del browser.

Next.js (servidor): apiFetch usa process.env.API_URL y el token puede venir de las cookies de la sesión SSR. El paquete api-client necesita soportar ambos contextos — o podés crear un helper separado para el server.

decisión pendiente — cómo obtiene datos la landing
Opción A

Via api-gateway

Next.js llama a tu API Express en el servidor. Misma fuente de datos que el frontend.

// Consistente con el resto del stack
const data = await fetch(
  `${process.env.API_URL}/technicians`
)

✓ Un solo lugar para lógica de negocio
✓ Mismo api-client que apps/web
⚠ Un hop extra de red (Next → api-gateway)
Opción B

Directo a Supabase

Next.js usa el SDK de Supabase directamente desde el servidor, sin pasar por tu API.

// Más simple para datos públicos
import { supabase } from '@myproject/supabase'
const { data } = await supabase
  .from('technicians')
  .select('*')
  .eq('available', true)

✓ Menos latencia (sin hop extra)
✓ Más simple para datos de solo lectura
⚠ Lógica de negocio duplicada fuera de la API
06 · Comunicación Frontend ↔ API

El paquete
api-client

Un paquete que enmascara todas las llamadas HTTP. El frontend importa funciones, no URLs.

💡 La idea central

No podés importar código de Express directamente en el browser. Lo que sí podés hacer es crear un paquete que envuelva los fetch() y los exponga como funciones tipadas. El browser sigue hablando por HTTP, pero tu código no lo sabe.

packages/types

Interfaces y DTOs compartidos entre frontend, API y microservicios. La fuente de verdad de tus modelos.

export interface User {
  id: string; email: string
  name: string; createdAt: string
}
export interface CreateUserDTO {
  email: string; name: string
}
packages/api-client

Fetchers puros. Sin React, sin estado. Solo funciones que hablan HTTP y devuelven tipos.

import { supabase } from '@myproject/supabase'
import type { User } from '@myproject/types'

export const usersApi = {
  getById:  (id: string) =>
    apiFetch<User>(`/users/${id}`),
  getAll:   () =>
    apiFetch<User[]>('/users'),
  create:   (data: CreateUserDTO) =>
    apiFetch<User>('/users', {
      method: 'POST',
      body: JSON.stringify(data)
    })
}
apps/web

El frontend no sabe nada de URLs, tokens ni fetch. Solo importa funciones tipadas.

// ❌ Sin el paquete
const res = await fetch('https://api.com/users/123', {
  headers: { Authorization: `Bearer ${token}` }
})

// ✅ Con el paquete
import { usersApi } from '@myproject/api-client'
const user = await usersApi.getById('123')

🔐 Auth automática

El apiFetch base lee el token de Supabase automáticamente. Ningún componente toca el token directamente.

// packages/api-client/src/client.ts
async function getAuthHeaders(): Promise<HeadersInit> {
  const { data: { session } } = await supabase.auth.getSession()
  return session
    ? { Authorization: `Bearer ${session.access_token}` }
    : {}
}

export async function apiFetch<T>(
  path: string, options?: RequestInit
): Promise<T> {
  const authHeaders = await getAuthHeaders()
  const res = await fetch(`${import.meta.env.VITE_API_URL}${path}`, {
    ...options,
    headers: { 'Content-Type': 'application/json', ...authHeaders, ...options?.headers }
  })
  if (!res.ok) throw new ApiClientError(await res.json())
  return res.json() as Promise<T>
}
07 · TanStack Query

El paquete
query-hooks

TanStack Query maneja la caché en memoria del browser. El frontend consume hooks, no fetchers.

🧠 El modelo mental de la caché

TanStack mantiene un objeto JS en la RAM del browser. Cada query guardada con su queryKey como clave. Si la data está "fresca" (staleTime no venció), la devuelve sin pegarle al servidor. Si venció, hace un refetch — pero igual muestra lo que tiene en caché mientras espera.

packages/query-hooks/src/keys.ts — query keys centralizadas
export const queryKeys = {
  users: {
    all:    () => ['users']               as const,
    byId:   (id: string) => ['users', id] as const,
  },
  orders: {
    all:    () => ['orders']                        as const,
    byUser: (uid: string) => ['orders', 'user', uid] as const,
  },
} as const
packages/query-hooks/src/useUser.ts
export function useUsers() {
  return useQuery({
    queryKey: queryKeys.users.all(),
    queryFn:  usersApi.getAll,
    staleTime: 1000 * 60 * 10, // 10 minutos
  })
}

export function useCreateUser() {
  const queryClient = useQueryClient()
  return useMutation({
    mutationFn: (data: CreateUserDTO) => usersApi.create(data),
    onSuccess: () => {
      // Marca la lista como stale → TanStack refetchea si hay
      // algún componente suscripto a esta key
      queryClient.invalidateQueries({ queryKey: queryKeys.users.all() })
    },
  })
}

❓ ¿Qué hace invalidateQueries?

Marca una entrada de la caché como stale (desactualizada). No la borra ni hace un refetch inmediato — simplemente le dice a TanStack que la próxima vez que un componente la necesite, vaya a buscar datos frescos al servidor. Si ya hay un componente montado y suscripto, el refetch ocurre inmediatamente.

cuándo pega y cuándo no pega a la API
t=0:00  → useUsers() → caché vacía       → GET /users  ✅ pega al servidor
t=0:01  → useUsers() → fresco (< 10 min) → usa caché  ❌ no pega
t=2:00  → useUsers() → fresco (< 10 min) → usa caché  ❌ no pega
t=10:01 → useUsers() → stale (> 10 min)  → GET /users  ✅ pega al servidor
         pero muestra la caché vieja mientras espera ↑

08 · Datos en tiempo real

Supabase Realtime
+ TanStack Query

Si usuario B modifica un pedido, usuario A lo ve sin hacer nada. Sin polling, sin requests innecesarios.

❌ Problema

El problema del staleTime

Si staleTime es 5 minutos, usuario A puede estar mirando datos desactualizados hasta 5 minutos después de que usuario B los modificó.

Usuario B modifica pedido #42
         ↓
Servidor actualizado ✅
         ↓
Usuario A... sigue viendo
pedido #42 viejo ⚠️
hasta que venza el staleTime
✅ Solución

WebSocket → invalidateQueries

Supabase Realtime escucha cambios en la DB y avisa al browser por WebSocket. TanStack refetchea automáticamente.

Usuario B modifica pedido #42
         ↓
Supabase detecta UPDATE
         ↓
WebSocket → browser A
         ↓
invalidateQueries → refetch
         ↓
Usuario A ve el cambio en ~100ms ✅
packages/query-hooks/src/useOrder.ts — hook con realtime
export function useOrder(id: string) {
  const queryClient = useQueryClient()

  // 1. Query normal de TanStack
  const query = useQuery({
    queryKey: queryKeys.orders.byId(id),
    queryFn:  () => ordersApi.getById(id),
    staleTime: 1000 * 60 * 5,
  })

  // 2. Suscripción a Supabase Realtime
  useEffect(() => {
    const channel = supabase
      .channel(`order-${id}`)
      .on('postgres_changes', {
        event:  'UPDATE',
        schema: 'public',
        table:  'orders',
        filter: `id=eq.${id}`   // solo este pedido
      }, () => {
        // Cuando llega el evento, invalida y TanStack refetchea
        queryClient.invalidateQueries({
          queryKey: queryKeys.orders.byId(id)
        })
      })
      .subscribe()

    // Cleanup: desuscribirse al desmontar el componente
    return () => { supabase.removeChannel(channel) }
  }, [id, queryClient])

  return query
}
SituaciónEstrategia recomendada
Datos que cambian raramentestaleTime generoso, sin más
Necesitás frescura pero no tiempo realrefetchInterval corto (polling)
Múltiples usuarios editando los mismos datosSupabase Realtime + invalidateQueries
Chat, notificaciones, dashboards en vivoSupabase Realtime directo

🔑 La regla de oro

Supabase Realtime reemplaza el polling. En vez de preguntar "¿cambió algo?" cada N segundos, el servidor te avisa cuando algo cambia. Menos requests, datos más frescos, mejor UX. Y ya lo tenés incluido en tu stack.
